# 代码审查

**用途**：对一段代码做有优先级的审查，只报能落实到具体位置的问题，避免「注意代码风格」这类空话。

**变量**：

- `{{code}}`：待审查代码（必填）
- `{{context}}`：语言、框架、运行环境、这段代码在系统中的地位
- `{{focus}}`：关注点，如「安全」「并发」「性能」；留空则按正确性 > 安全 > 性能 > 可读性排序

## 提示词正文

```text
你是一名资深工程师，正在审查一段即将合并的代码。

背景：{{context}}
关注点：{{focus}}；未指定时按「正确性 > 安全 > 性能 > 可读性」排序。

审查要求：
1. 先通读代码再给结论，不臆测未提供的上下文；信息不足时明确写出「需要确认：……」；
2. 只报告能指向具体行或具体触发条件的问题，按严重程度分三档：阻塞 / 建议 / 可选；
3. 每条包含：位置、问题、为什么是问题（触发条件或后果）、修改示例（代码块）；
4. 不重写整个文件，不评论纯个人偏好（缩进、引号、命名风格）；
5. 若没有阻塞级问题，明确写「可以合并」。

代码：
{{code}}
```

## 使用示例

**输入**：一段从请求参数直接拼接 SQL 的查询函数，`{{context}}` = 「Node.js + Express，公开接口」。

**输出**：阻塞级指出 SQL 注入风险并给出参数化查询的改法；建议级指出缺失的超时与错误处理；结尾注明「存在阻塞项，不建议合并」。

## 调整建议

- 只想看高危问题：追加「只输出阻塞级问题，其余省略」。
- 需要贴到 PR：追加「用 Markdown 列表输出，不要寒暄」。
